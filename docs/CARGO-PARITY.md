# Cargo parity audit and delivery gates

Audit date: **2026-11-16**. This is a source-based assessment and proposed plan, not a release announcement or a promise of delivery dates.

## Scope and evidence

Both repositories pin Goose `eadca409f68210893f366e60d0c2f0dc29a339be` in their [compiler pins](../GOOSE_REVISION) ([Honk pin](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/GOOSE_REVISION)). Status vocabulary:

- **Present, source-inspected**: explicit contract plus relevant implementation; not independently requalified here.
- **Partial**: a narrower capability exists, with the limitations stated.
- **Absent in inspected interface**: unsupported by the inspected manifest/CLI contracts; not a claim about every experimental branch.
- **In progress**: active parent implementation, without a passing receipt available to this audit.
- **Compiler prerequisite**: requires an upstream language/compiler capability or a demonstrated compatible implementation before Honk can promise it.

Honk's README distinguishes released v0.5.0-rc.1 from development Nest integration; the released prerelease does **not** include registries. Nest's README still directs users to `feat/nest-registry`. Honk's general reference still says general solving/backtracking is unimplemented, while the more specific registry contract and Nest solver implement bounded registry backtracking. Interpret this as a distinction between registry solving and the broader Git/path workflow, and reconcile these docs before publishing a parity claim. ## Delivery update: mixed-source discovery qualified

The later Honk implementation at [`5f2963c`](https://github.com/carabistouflette/honk/commit/5f2963c7194343db8517abb824c434eec9c8e4f7) removes root redeclarations for registry dependencies reached through Git/path manifests and legacy sourced-path imports. It discovers the Git/path closure, aggregates registry constraints, then solves and downloads registry packages. It preserves existing lock row order and lock bytes on frozen runs and failures. This update supersedes the **in progress** mixed-source row in the baseline assessment below; the broader parity gaps remain.

[Validation receipt](MIXED-SOURCE-VALIDATION.md) records eight mixed-source tests, 78 existing CLI tests, eight Git-version tests, eight mixed-source tests under ASan/UBSan and an independent exhaustive oracle across 160 seeded small graphs. [Raw before/after samples](validation/mixed-source-2026-11-16.json) retain binary identities and zero warm HTTP requests. Compiler changes are in scope, but multi-version compilation is not implemented by this delivery.

## Architectural limit: Cargo-like workflow within Goose's model

Goose defines a **root-owned, flat package graph, one version of each package per program**, because compilation and namespaces are global. Library sourced imports express requirements; the root owns declarations. Native `.build` sidecars and CMake integration belong to the compiler package mechanism. [Goose package design](https://aardappel.github.io/goose/docs/design/packages.html#43-root-only-and-flat), [Goose package usage](https://aardappel.github.io/goose/docs/packages.html).

Honk can discover transitives automatically and emit the complete compiler root mapping without making the user repeat them. That is compatible with root ownership. Supporting **multiple incompatible versions in one executable is not a package-manager-only change**: it requires compiler work on package identity, namespaces and potentially native linkage. Choosing another resolver or inventing aliases is not evidence that this constraint disappeared. Nest currently selects one version per registry/package, and Honk additionally has global import aliases. [Nest protocol](PROTOCOL.md), [Honk graph implementation](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/src/deps.goose), [Goose design decisions](https://aardappel.github.io/goose/docs/design/packages.html#1-decisions).

Cargo can retain multiple SemVer-incompatible versions when necessary, while trying to unify compatible ones; it backtracks under constraints and generally prefers higher versions, with lock and compiler-version policy affecting choices. This is a material semantic difference, not a missing CLI flag. [Cargo resolver](https://doc.rust-lang.org/cargo/reference/resolver.html).

**Delivery decision:** full Cargo parity includes Goose compiler changes for incompatible package versions. The current flat graph is the compatibility baseline, not the final product scope. Implement and qualify package identity, scoped dependency bindings and generated symbol isolation before enabling multi-version resolution. Compiler changes must preserve current behavior until an explicit, tested transition is available. “SOTA” means measured correctness, useful diagnostics, predictable resources, reproducibility and competitive end-to-end performance. It is not equivalent to selecting a buzzword algorithm such as PubGrub, SAT or CDCL. Nest explicitly calls its current solver bounded chronological backtracking and disclaims optimal adversarial complexity. [Nest solver contract](PROTOCOL.md).

### Build, test, benchmark, documentation and lint

Cargo supplies build/check/run, test orchestration including unit/integration/doc tests, benchmark orchestration and rustdoc documentation generation. `cargo bench` is stable, but Rust's built-in `#[bench]` remains nightly; stable custom harnesses are supported. [Build](https://doc.rust-lang.org/cargo/commands/cargo-build.html), [test](https://doc.rust-lang.org/cargo/commands/cargo-test.html), [bench](https://doc.rust-lang.org/cargo/commands/cargo-bench.html), [doc](https://doc.rust-lang.org/cargo/commands/cargo-doc.html).

Honk has **present, source-inspected** build/run/check, standalone test/bench execution, glob target filters, formatting, install/uninstall, source packaging and API declaration dump. Its `doc` writes `target/doc/NAME.goose`; this is **not evidence of rustdoc-style HTML, linked dependency documentation or doctests**. Development test jobs are bounded 1–8, compile sequentially and run cohorts; cancellation/deadline/descendant limitations remain documented. [CLI reference](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/docs/REFERENCE.md), [README](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/README.md), [parallel contract](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/docs/parallel-tests.md), [command implementation](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/src/commands.goose).

Cargo's `[lints]` is built-in configuration, while Clippy and rustfmt are separate official toolchain tools exposed as Cargo subcommands. Honk's `fmt` and compiler `check` do not establish Clippy-equivalent lint coverage, configurable lint groups or workspace lint inheritance. [Cargo manifest lints](https://doc.rust-lang.org/cargo/reference/manifest.html#the-lints-section), [Clippy usage](https://doc.rust-lang.org/clippy/usage.html), [rustfmt](https://github.com/rust-lang/rustfmt), [Honk commands](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/docs/REFERENCE.md).

### Build artifacts and incremental work

Cargo retains final/intermediate artifacts, separates target/profile outputs and cooperates with rustc incremental compilation. The incremental compiler cache is distinct from an external compiler cache. [Cargo build cache](https://doc.rust-lang.org/cargo/reference/build-cache.html), [profile incremental setting](https://doc.rust-lang.org/cargo/reference/profiles.html#incremental).

Honk's **partial** `--reuse-build` is opt-in and off by default: verified whole executables can skip compilation for eligible source-only build/run/test inputs. Native sidecars, externs, embeds and unsupported configurations fall back to compilation. Compiler/artifact/source/environment bytes enter the key, but indirect system compiler/linker/sysroot inputs are not completely tracked; those must stay unchanged or users must clean. Tests always execute. Sixteen fixed test buckets per profile limit entry count but can consume up to 4 GiB plus the build/run slot. This is neither fine-grained incremental Goose compilation nor a hermetic remote cache. [Reuse contract](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/docs/INCREMENTAL-BUILDS.md), [implementation](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/src/build_cache.goose).

Goose itself caches runtime/package native parts per C compiler. That compiler cache is separate from Honk's executable reuse and Nest's content-addressed source archive cache. Avoid counting all three as one implemented incremental-build capability. [Goose package usage](https://aardappel.github.io/goose/docs/packages.html), [Nest protocol](PROTOCOL.md), [Honk reuse](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/docs/INCREMENTAL-BUILDS.md).

### Robustness and security

Cargo's registry index includes archive checksums and yanked state; build scripts can execute package-supplied build logic. Neither checksum verification nor Cargo-style build orchestration should be described as publisher authentication or a code sandbox. [Registry index](https://doc.rust-lang.org/cargo/reference/registry-index.html), [build scripts](https://doc.rust-lang.org/cargo/reference/build-scripts.html).

Nest has **present, source-inspected defenses**: TLS verification, SHA-256 archives, restrictive archive extraction, explicit size/work bounds, atomic cache installation and rehashing of extracted tree contents, including same-size/mtime edits. Its trusted-local-cache model excludes hostile same-user replacement of sources and seals and complete rollback. HTTPS URLs are trusted inputs, not an SSRF sandbox; no publisher identity or power-loss durability guarantee follows from hashes/renames. [Protocol and exact limits](PROTOCOL.md), [native adapter](../native/nest.c), [adversarial fixtures](../tests/integration.py), [native tests](../tests/native.c).

Honk rejects source symlinks/special files, constrains Git transport, verifies compiler revision identities, uses project/cache locks and preserves last-good executables after compilation failure. Trusted compiler/native dependencies still execute code; direct-child signal handling does not supervise arbitrary descendants. Revision checking of an explicitly supplied compiler does not authenticate executable bytes. These are documented boundaries, not completed supply-chain attestation or sandbox guarantees. [Reference](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/docs/REFERENCE.md), [security policy](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/SECURITY.md).

**Assessment:** these are useful focused defenses, but no independent security audit or systematic superiority over Cargo is established here. Existing fixture code is coverage evidence, not a fresh passing test receipt. Fuzzing, malicious metadata/archive cases, crash recovery, concurrency and secret-redaction checks belong in release gates.

## Stable built-ins, companion tools and unstable features

Do not inflate the Cargo target by treating every Rust tool as a Cargo built-in:

| Category | Examples and implications |
| --- | --- |
| Stable Cargo | Dependency resolution, source declarations, workspaces, lock/offline flags, targets/profiles, metadata/tree, packaging/publication commands, vendor/replacement and registry credential integration are documented above. Registry servers must implement corresponding APIs; Cargo alone is not the registry service. [Registries](https://doc.rust-lang.org/cargo/reference/registries.html). |
| Official companion tools | Clippy provides lints; rustfmt provides formatting. Their subcommand spelling does not make their analysis engines Cargo built-ins. [Clippy](https://doc.rust-lang.org/clippy/usage.html), [rustfmt](https://github.com/rust-lang/rustfmt). |
| Third-party ecosystem | nextest is an alternative test runner; Criterion provides statistical benchmarking; cargo-audit checks advisories; cargo-deny checks dependency policies; sccache caches compiler results, including remote storage options. They are optional integrations, not stable Cargo requirements. No upstream speed slogan is imported as benchmark evidence. [nextest](https://nexte.st/), [Criterion](https://github.com/bheisler/criterion.rs), [RustSec tooling](https://rustsec.org/), [cargo-deny](https://embarkstudios.github.io/cargo-deny/), [sccache](https://github.com/mozilla/sccache). |
| Unstable/nightly | The inspected unstable reference lists minimal-version resolution, `build-std`, checksum freshness and SBOM precursor generation behind unstable interfaces. Rust's `#[bench]` is also unstable, although Cargo's bench command/custom harness path is stable. Track these separately from stable parity and recheck their status before implementing equivalents. [Unstable reference](https://doc.rust-lang.org/cargo/reference/unstable.html), [bench distinction](https://doc.rust-lang.org/cargo/commands/cargo-bench.html). |

For KISS, prefer stable graph metadata and a small external-tool interface over embedding every audit, statistical runner or remote cache into the package manager. This is a design recommendation, not a statement that such a Goose ecosystem exists today.

## Phased work with acceptance criteria

All items below are **proposals**, except the explicitly marked mixed-source work already in progress. Sequence expresses dependencies, not shipping dates. Each phase requires a retained receipt with exact sources, toolchains, commands, outputs and failure cases before changing status to implemented.

### Phase 1 — Complete and qualify mixed-source resolution (in progress)

Acceptance:

1. Root → path → registry, root → Git → registry, multi-level Git/path chains and mixed-source diamonds fetch and compile without redundant registry declarations at the application root. Include a legacy sourced-import chain that reaches a manifest with registry requirements.
2. Constraints discovered through different paths participate in one consistent resolution: a late narrow requirement can force an earlier choice to backtrack; incompatible requirements fail with both chains shown. Alias collisions, cycles and compiler-pin mismatch fail explicitly.
3. Direct and transitive registry dependencies resolve identically regardless of discovery order; development dependencies of non-root packages are not accidentally promoted. Registry archive restrictions remain explicitly enforced until a separately designed schema changes them.
4. Commit the resulting lock in a fixture. With the index removed and network trapped, cached `fetch/check/build --frozen` succeeds; a missing archive fails without requests. Valid lock online cache miss fetches only required blobs. `--locked` failures leave old lock bytes intact; failed resolution cannot publish a partial graph.
5. Add focused CLI fixtures to the existing [Honk registry suite](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/tests/registry_cli.py), and run that suite plus relevant Git/path graph, Nest core, extraction and integration tests against the actual new binary. Existing standalone registry coverage is in [Nest integration](../tests/integration.py); it does not alone prove mixed-source closure.

Benchmark gate: compare before/after whole commands on unchanged direct-registry cases and newly supported mixed-source cases. The old binary's unsupported case is a correctness failure, not a latency baseline. Count metadata/blob requests; warm frozen fetch must make **zero** network requests. Report closure size and solver decisions separately from source validation time.

### Phase 2 — Workspace graph and reproducible source controls

Acceptance: implement one root lock and deterministic workspace graph with explicit schema/migration behavior; root/member commands agree on selected versions; package/dependency inheritance has documented precedence and unknown keys fail; conflicting compiler pins produce a useful error. Decide whether the workspace enforces one version globally or only per program; test that choice against the flat compiler model. Multi-member lock publication must be atomic at the chosen root boundary and failure must preserve the old valid lock.

Add graph-wide override semantics, a vendor export and identity-preserving source replacement as distinct operations. Accept only when a fresh cache plus exported vendor tree builds frozen without the original network sources; tampering fails; graph metadata preserves original identity separately from local replacement location. Include collision, traversal and nested-workspace cases. These extend gaps identified in [Honk's current workspace/packaging contract](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/docs/REFERENCE.md), rather than renaming existing per-member locks.

Benchmark gate: 1/8/32-member workspaces, shared diamonds and repeated root/member invocations. One invocation must not refetch the same unchanged index for each member; retain peak RSS, staging bytes and request counts. Compare shared-lock benefits against the previous per-member workflow without hiding migration costs.

### Phase 3 — Feature and compilation configuration contract

Acceptance: first document and demonstrate a compiler mechanism for conditional Goose declarations/imports. Then add optional/default/additive features, forwarding and target predicates with one canonical normalized representation. Verify empty/default/all/selected feature sets, dev and host/target separation, missing feature errors and reproducible lock behavior. Disabled dependencies must not become hidden compiler fetches. A manifest-only toggle that leaves unconditional imports broken does not pass.

Add target/profile selection only for compiler-supported settings. Cross compilation passes only with an explicit host/target toolchain model, native sidecar dependencies, separate artifacts and a configured execution runner. Prove at least one non-host target builds and one target runner executes tests; diagnose unsupported configurations before publishing outputs. Multiple incompatible versions remain blocked on compiler work and a separate identity/linkage design.

Benchmark gate: default-feature overhead versus Phase 2, feature-matrix scaling, profile/target switch invalidation and native builds. Count separately resolver work, compiler work and external toolchain setup; do not attribute C compiler speed changes to package resolution.

### Phase 4 — Publishing and registry lifecycle

Acceptance: define API/versioning and server authorization before adding publish/login/owner/yank commands. Test dry-run, exact exported-tree verification, duplicate-version refusal, permissions/revocation, alternate registry isolation and yank/undo with old locks. Credentials must never cross an unrelated redirect origin or appear in manifests, locks, logs or error output; integrate OS-backed/external credential storage through a small contract rather than embedding plaintext tokens by default.

A backend must demonstrate ownership verification and safe concurrent publication. Static public hosting can remain an explicit supported deployment mode, but a local packaging command cannot satisfy hosted publication. These are new requirements beyond [Nest's reviewed-PR publication model](../README.md).

Benchmark gate: record upload/download bytes, concurrent publish conflict outcomes and bounded timeout/retry behavior using local fixtures. Security/correctness failures block the phase regardless of latency.

### Phase 5 — Developer workflow and safe build performance

Acceptance: version resolved graph metadata, stable IDs and query semantics; document streaming/failure behavior. Add inverse tree/conflict explanations, configurable lint integration and a deliberate doc/doctest contract. Test/bench output must distinguish compile/run failures and expose machine-readable results without dropping child failures. Keep custom benchmark runners separate from statistical claims.

Improve default no-op/edit builds only after expanding the build-input model: demonstrate invalidation for source, native files, embeds, compiler/linker/sysroot, environment, profiles and targets. Unsupported inputs must safely compile; cache corruption must miss/fail safely. Claim fine-grained incremental compilation only with compiler evidence, and remote reuse only with a defined artifact trust model. The current [opt-in reuse limitations](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/docs/INCREMENTAL-BUILDS.md) remain in force until replaced by tests and documentation.

Benchmark gate: cold build, warm no-op, one-leaf edit, root edit, native header edit, feature/profile/target changes, test compilation and execution. Check output equivalence, failure preservation and cache hit/miss reasons. Record disk use alongside latency/RSS; bounded entry counts alone do not demonstrate acceptable storage.

## Cross-phase benchmark and release gate

Proposed measurement protocol:

- Pin exact baseline/candidate binaries, compiler, dependency sources and Cargo **stable** comparator version. Record OS/CPU, filesystem, environment policy, limits and fixture hashes. Use local registry fixtures for repeatability; Internet latency is a separate workload.
- Use at least three untimed warmups and 31 alternating paired samples for short warm commands. For expensive cold builds, retain at least seven independent runs and explain reset policy. Keep raw samples, median, p95, ranges and maximum RSS; disclose shared-host interference and process-versus-aggregate memory semantics.
- Cover chains, wide graphs, diamonds, many releases, near-unsatisfiable and unsatisfiable graphs, lock-only cache hits, corrupt cache and explicit resource exhaustion. Include near-limit valid graphs; report refusal at documented caps rather than silently reducing workloads.
- Suggested regression threshold: investigate and block unexplained warm median regressions above 5% **and** 1 ms, or p95 regressions above 10% **and** 2 ms, on unchanged workflows in two controlled repeats. Block unexplained peak RSS/disk regressions above 10% and 1 MiB. These are proposed gates, not existing measured guarantees; approve documented correctness/resource tradeoffs explicitly.
- Resolver validity and deterministic policy take priority over speed. Use a small independent exhaustive oracle for bounded single-version graphs; compare Cargo only on the shared semantic subset. Multi-version Cargo success versus Goose flat-graph failure is a capability gap, not a resolver timing result.
- A claimed improvement must identify the winning workload and retain slower cases. “SOTA” needs competitive representative evidence and adversarial robustness; no single fetch ratio establishes universal superiority.

Existing Nest measurements cover a synthetic 25-package warm locked offline fetch, not compilation or hard constraint graphs; their Cargo comparator was **1.101.0-nightly**, so they do not establish performance against a pinned stable Cargo release. The documented lower Honk latency belongs only to that scenario. Honk's measurement guide likewise separates functional smoke receipts from timing evidence. [Nest benchmark scope and comparator](../bench/README.md), [raw measurements](../bench/results.json), [Honk measurement guide](https://github.com/carabistouflette/honk/blob/d9577d2167bbf456102970fc0d854e7077beca03/bench/README.md).
